# ۰۶ — چندزبانگی و RTL

## ۱. زبان‌های پشتیبانی‌شده

| زبان | کد | جهت | تقویم پیش‌فرض | اعداد پیش‌فرض |
|---|---|---|---|---|
| فارسی | `fa` | RTL | شمسی | فارسی (۱۲۳) |
| English | `en` | LTR | میلادی | لاتین (123) |
| Türkçe | `tr` | LTR | میلادی | لاتین (123) |
| العربية | `ar` | RTL | میلادی/قمری | عربی (١٢٣) |

هر کدام از این موارد در تنظیمات کاربر قابل بازنویسی است (مثلاً فارسی + تقویم میلادی).

## ۲. Translation Database — قانون بنیادی

> **هیچ رشتهٔ نمایشی در کد hard-code نمی‌شود** — نه در Backend، نه در Flutter.

### جدول
```
translations
  id · locale · group · key · value · is_overridden · updated_at
  UNIQUE(locale, group, key)
  INDEX(locale, updated_at)
```

نمونه:
```
locale=fa  group=transaction  key=create.title      value="ثبت تراکنش"
locale=en  group=transaction  key=create.title      value="New Transaction"
locale=tr  group=transaction  key=create.title      value="Yeni İşlem"
locale=ar  group=transaction  key=create.title      value="معاملة جديدة"
```

### جریان کار
1. توسعه‌دهنده کلید را در کد استفاده می‌کند: `t('transaction.create.title')`
2. دستور `php artisan i18n:scan` کلیدهای جدید را پیدا و در DB با مقدار خالی ثبت می‌کند
3. پنل ترجمه (Backoffice) کلیدهای بدون ترجمه را برای هر زبان فهرست می‌کند
4. CI اگر کلیدی در `fa` یا `en` ترجمه نشده باشد **هشدار** می‌دهد (برای `tr`/`ar` مسدودکننده نیست)

### تحویل به کلاینت
```
GET /api/v1/translations/fa?since=2026-07-01T00:00:00Z
→ { "data": { "transaction.create.title": "ثبت تراکنش", ... },
    "meta": { "version": 184, "checked_at": "..." } }
```
- کلاینت ترجمه‌ها را محلی cache می‌کند و فقط delta می‌گیرد
- تغییر ترجمه **بدون انتشار نسخهٔ جدید اپ** به کاربر می‌رسد
- ARB به‌عنوان fallback آفلاین درون باندل اپ باقی می‌ماند

## ۳. RTL/LTR

### قواعد اجباری در Flutter
- استفاده از `EdgeInsetsDirectional` و `AlignmentDirectional` — **هرگز** `EdgeInsets.only(left:)`
- `TextDirection` از `Localizations` گرفته می‌شود، نه از ثابت
- آیکون‌های جهت‌دار (بازگشت، فلش، پیشرفت) با `Directionality` معکوس می‌شوند
- نمودارها در RTL باید محور و راهنما را معکوس کنند
- اعداد و مبالغ همیشه LTR رندر می‌شوند حتی در متن RTL (با `Bidi` isolate)
- تست **Golden** برای هر صفحه در دو حالت `fa` و `en`

### متن دوجهته (Bidi)
`«۳۵۰ TRY در Starbucks»` — ترکیب RTL و LTR باید بدون به‌هم‌ریختگی نمایش داده شود.
از `⁨` (FSI) و `⁩` (PDI) برای isolate کردن قطعات LTR در متن RTL استفاده می‌شود.

## ۴. اعداد، تاریخ و ارز

### اعداد
- ذخیره: همیشه لاتین در DB
- ورودی: کاربر می‌تواند `۱۲۳` یا `١٢٣` یا `123` وارد کند → نرمال‌سازی در ورودی
- خروجی: بر اساس تنظیم کاربر

### تاریخ
- ذخیره: UTC / ISO-8601
- نمایش: شمسی (`jalali`)، میلادی، یا قمری بر اساس تنظیم Workspace + کاربر
- کتابخانه: `shamsi_date` در Flutter، `morilog/jalali` در Laravel
- **هرگز** تبدیل تقویم در لایهٔ دیتابیس انجام نمی‌شود

### ارز
- قالب‌بندی بر اساس `locale` + `currency`:
  - `fa` + `IRR` → `۵۰۰٬۰۰۰ ریال`
  - `en` + `USD` → `$500.00`
  - `tr` + `TRY` → `₺500,00`
  - `ar` + `AED` → `٥٠٠٫٠٠ د.إ`
- جای نماد ارز (قبل/بعد) از جدول `currencies` خوانده می‌شود

## ۵. جمع و مفرد (Pluralization)

از قواعد ICU استفاده می‌شود؛ عربی شش شکل جمع دارد و **باید** پشتیبانی شود:

```
en: {count, plural, one {# transaction} other {# transactions}}
fa: {count, plural, other {# تراکنش}}
ar: {count, plural, zero{...} one{...} two{...} few{...} many{...} other{...}}
```

## ۶. محتوای کاربر در برابر محتوای سیستم

| نوع | مثال | رفتار |
|---|---|---|
| سیستم | «ثبت تراکنش»، نام دسته‌های پیش‌فرض | از Translation DB، همیشه ترجمه |
| کاربر | نام حساب «کارت ملی»، توضیح تراکنش | ذخیرهٔ عین متن، بدون ترجمه |

دسته‌های پیش‌فرض با `name_key` ذخیره می‌شوند تا در هر زبان درست نمایش داده شوند؛
اما به‌محض ویرایش توسط کاربر، به متن ثابت تبدیل می‌شوند.

## ۷. جستجو و نرمال‌سازی فارسی/عربی

پیش از ایندکس و پیش از جستجو، این نرمال‌سازی‌ها اعمال می‌شوند:
- `ي` → `ی` ، `ك` → `ک`
- حذف اعراب و تشدید
- نیم‌فاصله (`‌`) → فاصلهٔ عادی برای ایندکس
- اعداد فارسی/عربی → لاتین
- حذف کشیده (`ـ`)

این منطق در یک کلاس واحد `TextNormalizer` قرار می‌گیرد و هم در Backend و هم در Flutter
(برای جستجوی آفلاین) پیاده می‌شود — با تست‌های مشترک.
